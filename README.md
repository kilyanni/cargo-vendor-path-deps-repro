# `fetchCargoVendor` doesn't rewrite intra-workspace path deps (minimal repro)

When `fetchCargoVendor` vendors a crate from a git source, it copies the
crate dir verbatim into the flat vendor layout (`source-git-N/<crate>-<ver>/`)
without rewriting `path = "..."` declarations that pointed at sibling crates
in the original monorepo. Upstream `cargo vendor` does perform this rewrite.

In most builds this is invisible — when the vendored crate is reached through
a git source, cargo's resolver uses the lock to find sub-deps and ignores the
stale path declarations. But when a downstream cargo invocation reaches the
vendored crate via a **path source** (e.g. the wbuild crate generated by
`substrate-wasm-builder`, which path-depends on the vendored runtime), cargo
treats that subtree as local-dev and follows the path declarations literally,
hitting ENOENT on the now-broken monorepo paths.

## Repo layout

- Root is a Cargo workspace with two crates:
  - `crate-a/` — declares `crate-b = { path = "../crate-b" }`. This is the
    path declaration that breaks after flattening.
  - `crate-a/build.rs` — mimics `substrate-wasm-builder`: generates a stub
    `wbuild` crate at `$OUT_DIR/wbuild/` that path-depends on crate-a's
    `CARGO_MANIFEST_DIR`, then spawns a nested `cargo build` on it.
  - `crate-b/` — trivial sibling crate.
- `repro/` — a downstream crate that depends on `crate-a` via a git source
  pointing at this same repo. Building it triggers crate-a's build script,
  which spawns the nested cargo, which traverses crate-a as a path source
  and follows the broken `path = "../crate-b"` to ENOENT.

## Reproducing

From `repro/`:

1. Generate a lock file (needs network — fetches crate-a from this repo):
   ```
   cargo generate-lockfile
   ```
2. Run the Nix build:
   ```
   nix build .
   ```
   The first invocation will fail with a `cargoHash` mismatch — paste the
   suggested hash into `repro/package.nix` and rerun. The second run fails
   with the actual repro:
   ```
   error: failed to read `/build/repro-0.1.0-vendor/source-git-0/crate-a-0.1.0/../crate-b/Cargo.toml`
   ```

## Why the outer `cargo build` succeeds but the nested one fails

When the outer cargo reaches `crate-a` via a **git source** (the dep declared
in `repro/Cargo.toml`), it consults the lock to resolve `crate-a`'s sub-deps.
The lock pins `crate-b` to a git source (the same upstream repo), so cargo
uses the vendored `source-git-0/crate-b-0.1.0/` and ignores the broken
`path = "../crate-b"` declaration. Outer build proceeds.

The nested cargo invocation reaches `crate-a` via a **path source** (the
generated `wbuild-stub` crate's `crate-a = { path = "..." }` dep). From a
path-source parent, cargo's resolver treats the subtree as a local-dev
workspace and follows each `path = "..."` literally — including the
post-flattening-broken `../crate-b`. ENOENT.

This mirrors the failure mode that hits any `substrate-wasm-builder`-based
package built through nixpkgs today.

## Suggested fix

Have `fetchCargoVendor` perform the same path-dep rewrite that upstream
`cargo vendor` does on the vendored Cargo.toml files in `source-git-*/`. A
Python implementation of just the rewrite step (used as a `postPatch`
workaround in one nixpkgs package) is short — under 80 lines using stdlib
`tomllib` — so the change to `fetchCargoVendor` itself should be modest.
